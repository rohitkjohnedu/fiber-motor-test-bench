## 1. Project Overview
`futek_reader.py` is a standalone PyQt6 GUI for reading the FUTEK IPM650 force sensor
(connected to a LRF400 load cell) via the FUTEK USB DLL (pythonnet / C# interop).
It provides COM port discovery, live force readout, live plot, and device register inspection.

- Added `DISPLAY_UNITS` dict: `mN`, `N`, `gf`, `lb` with mN-based scale factors.
- `QComboBox` in Force Reading group; switching unit rescales both the live readout
  and the plot y-axis instantly without reconnecting.

### 3.2 Sensor S/N Read-back
- `Get_Device_Serial_Number` inspected — takes a **device index string**, not a handle.
  Calling it with an `IntPtr` throws a .NET type-mismatch exception.
- `Get_Sensor_Identification_Number(handle)` returns `'Error'` for this hardware
  (LRF400 has no TEDS chip; S/N is only on the physical label).
- Resolution: `device_sn = self.serial_number` (already known from connection);
  `sensor_id` shown as-read (displays `'Error'` if unsupported).

### 3.3 Capacity Override Field
- `Capacity:` `QLineEdit` + unit `QComboBox` added to Connection group.
- Auto-filled on connect (value in mN, unit set to `mN`).
- User can type e.g. `0.25` + select `lb` → internally converts to

### 3.6 Unit shown in readout

## 4. Bug Fixes

### 4.1 Connection Error "Device Error 0 / Impossible to connect"
- **Root cause:** `Get_Device_Serial_Number(device_handle)` — added to
  `_get_devices_parameters()` — does not accept an `IntPtr` argument.
  The resulting .NET exception was silently caught by a bare `except:` block,
  which then printed the misleading error message.
- **Fix:** Replaced `Get_Device_Serial_Number(handle)` with
  `self.device_sn = self.serial_number` (already known).
- **Secondary fix:** Changed `except:` → `except Exception as exc:` so the
  actual exception message appears in the error dialog.

### 4.2 Wrong Capacity Auto-Detection
- **Root cause:** The IPM650 stores capacity with `unit_code = 20` (lb) in
  register 6, but earlier ad-hoc tests showed `unit_code = 5` (gram) because
  a different device responded at that time.
- The `FUTEK_UNITS_CODE` dict in `ForceSensor/futek.py` was written manually
  (not from official FUTEK documentation); its correctness for all unit codes
  is unverified.
- **Current state:** With the correct device connected, `unit_code = 20` (lb)
  gives `0.25 × 4448.2 = 1112 mN` — matches the LRF400 label.

### 4.3 Register Panel Showing "Error reading registers"
- **Root cause 1:** Font set via `self.registers_display.font().__class__(...)` —
  `QFont` was never imported. Fixed by adding `from PyQt6.QtGui import QFont`.
- **Root cause 2:** `_update_registers()` was called after `start_recording()`,
  so the background thread was already polling the DLL. Concurrent DLL calls
  caused `Get_Internal_Register` to return `'Error'`, and `int('Error')` raised
  `ValueError`.
- **Fix:** Moved `_update_registers()` call to **before** `start_recording()`.
- **Defensive fix:** Wrapped entire method in `try/except` to display errors
  inline rather than silently failing.

## 5. Open Questions / Known Limitations

- **Force value mismatch vs IPM650 display:** The software formula subtracts
  `tare_register_value` (register 1, currently = 0) rather than the zero-offset
  (register 2 = ~8 388 411). Without pressing **Tare**, the zero-load reading
  is non-zero. Users must tare the software to align with the IPM650 display.
- **LRF400 S/N not readable electronically:** No TEDS chip; S/N must be read
  from the physical label and entered manually if needed.
- **`FUTEK_UNITS_CODE` accuracy:** Mapping of unit code integers to unit names
  is unverified against official FUTEK documentation. `unit_code = 20 = lb`
  appears correct for the tested sensor but has not been confirmed from docs.
- **DLL thread safety:** `Get_Internal_Register` (and likely other read calls)
  must not be called while the background `Normal_Data_Request` polling thread
  is running. All register reads must happen before `start_recording()`.
